# WSL baseline after the kernel correctness and benchmark fixes

22 September 2026. Source base: `6ea2939` on `a5-arm-throughput`, with the local
NEON flush and kernelbench thread-count changes. Exact changed-source hashes,
model hash, toolchain and host are in [metadata](WSL-20260922-metadata.json).
This establishes a local baseline; it is not an interleaved before/after
speedup experiment. The fixes do not change the x86 production kernels.

## What changed

Baseline NEON now flushes i16 accumulators every 16 beats even when the current
beat has no weights. Previously an early `continue` could bypass the flush and
allow overflow. The differential corpus adds 3,072-column rows with zero beats
at positions 16, 32 and 48, both weight signs, and activations of -128 and +127.
The compiled ARM kernel failed under QEMU before the fix and passes afterward:
for the negative-weight/-128 case, the old result was -155648 instead of 368640.

Kernelbench now accepts one `--threads N` per process (default 1), initializes
and reports the actual pool width, and uses that count for its cached ternary,
streaming ternary and dense measurements. Before this change, a same-process
sweep initialized a two-thread pool and then silently ran widths 4/8/16/32
serially. `--list-kernels` lists the supported kernels without running the
benchmark. CI invokes separate processes and runs the CLI regressions.

The global pool's fixed-width lifetime remains unchanged. Library clients that
request different widths in one process still fall back to serial execution
for the later widths; that API behavior is separate from this benchmark fix.

## Reproduce the measurements

From the repository root, after other tests/builds have completed:

```sh
cargo build --release --locked -p tritd
cargo build --release --locked -p trit-cpu --example kernelbench
export CARGO_TARGET_DIR="$PWD/target"
for T in 1 2 4 8 16; do
    bash benches/run.sh --model models/bitnet-2b4t.trit --tokens 32 \
        --threads "$T" --out /tmp/tritium-wsl-baseline.csv
done
for T in 1 2 4 8 16; do
    target/release/examples/kernelbench --threads "$T"
done
```

The full-model harness warms the model and takes three runs over the four short
prompts, with each thread count in a separate process. It reports the median
across the prompt/run decode rates. TTFT remains the minimum across those
samples; it is **not** median or fixed-256-token latency. RSS is a high-water
mark in MiB despite the CSV's `peak_rss_mb` name. Achieved GB/s is effective
weight traffic, not a memory-controller counter. The streaming-probe denominator
is measured in the same invocation.

Neither an energy counter nor configured llama.cpp/bitnet.cpp baseline binaries
are available in this working setup. **Correction, 2026-09-23:** the baseline
half of that was wrong. Both `llama-bench` builds and both GGUFs were present
in `~/.cache/tritium-baselines` the whole time; only the harness environment
variables were unset. The three-way comparison was re-run the next day and is
in [WSL-20260923-compare.md](WSL-20260923-compare.md). The energy half stands:
no RAPL zone is exposed here. The CSV records unavailable baseline rows
explicitly. No ARM or FPGA performance claim is made. The kernelbench timing
samples are diagnostics, not full-model tokens/second; its projected column is
labelled accordingly.

## Verification

- The new benchmark CLI tests failed against the original executable and pass
  with the fix, covering thread consistency, invalid arguments and listing.
- Standard release workspace suite: 137 passed, zero failed, three ignored
  asset-dependent tests. The explicit real-checkpoint comparison also passed:
  eight positions in each of Reference, Folded and IntMlp, with cosine displayed
  as 1.000000 and identical top-1 IDs throughout.
- Forced x86 differential suites: 40 passed across scalar, AVX2, AVX-512BW and
  AVX-512 VNNI. Optional bitserial forced-corpus check passed.
- ARM differential suites: 30 passed across scalar, NEON and NEON dot-product
  **under QEMU emulation**, using the actual aarch64 musl binaries.
- Formatting, host clippy and aarch64 clippy/cross-compilation passed.
- Independent read-only review found no actionable issues.

For reproducing the ARM correctness check on an x86 Linux host with
`qemu-aarch64-static` available (never use this for throughput):

```sh
rustup target add aarch64-unknown-linux-musl
export CARGO_TARGET_AARCH64_UNKNOWN_LINUX_MUSL_LINKER="$(rustc --print sysroot)/lib/rustlib/x86_64-unknown-linux-gnu/bin/rust-lld"
export CARGO_TARGET_AARCH64_UNKNOWN_LINUX_MUSL_RUNNER=qemu-aarch64-static
for K in neon neon-dotprod scalar; do
    TRIT_CPU_KERNEL="$K" cargo test -p trit-cpu --release --locked \
        --target aarch64-unknown-linux-musl --test differential
done
```

The existing native ARM CI job also receives the added corpus. A native CI rerun
has not been triggered here; physical target devices remain unavailable.
No RTL source changed in this patch.

## Measured full-model results

| Threads | Decode tok/s | Reported TTFT minimum (ms) | Peak RSS (MiB) |
|---|---|---|---|
| 1 | 15.80 | 427.2 | 1221 |
| 2 | 23.99 | 260.3 | 1221 |
| 4 | 25.42 | 257.2 | 1221 |
| 8 | 24.43 | 273.1 | 1220 |
| 16 | 20.09 | 331.2 | 1218 |

The peak remains at four threads, with declines at eight and sixteen. This is
a fresh sample of the existing scaling limitation, not a demonstrated speedup
or regression against the August measurements. Timing on this host varies;
comparative optimization claims need interleaved runs.
